# Automatic workflows — v0.3.0

## What runs without a manual MCP request

After installation, restart the host and approve/trust the hook definitions in its native interface. Command hooks are run by the host lifecycle, independently of whether the main language model elects to invoke an MCP tool. They use the same configured System One client and judgment implementations as the MCP server.

| Trigger | Both clients | Automatic behavior |
|---|---|---|
| Session start/resume | Yes | Add the proactive tool-selection and verification policy. |
| User prompt | Yes | Begin a fresh evidence ledger; add a compact policy reminder. Preserve evidence only for an exact continuation generated by this bridge. |
| Tool start | Yes, for matched host tools | Record the actual start of a shell/check/edit operation. No provider call. Never approve or rewrite the tool. |
| Tool completion | Yes, for matched host tools | Record result and exit status. A completed result without an observed start cannot certify a fresh check. |
| Failed tool | Claude failure event; Codex result event | Record failure; do not misread a failing test as a passing command. |
| External fetch result | Matching WebFetch / MCP fetch, search or read_resource | Run an advisory System One screen if the complete result fits the screen budget. Do not replace output or treat a screen as an injection-proof security boundary. |
| Agent Stop | Yes | Check completion against observed edits and fresh verification; automatically request follow-up when warranted. |
| Stop after fresh passing checks | Yes | Run a combined patch/completion gate, including an assessment of whether the final message actually claims completion. |
| Subagent start/stop | Yes | Inject policy into the child and review the child's completion, using its own transcript or event ledger. |
| Task marked complete | Claude only | Check that task's status transition. A block is emitted as exit **2** with stderr feedback. |
| Native PreCompact, manual or auto | Yes | Request System One retention decisions and write a private checkpoint without editing the host transcript. |
| SessionStart after compaction | Yes | Reinstate the tool policy, even when no checkpoint exists. Restore any eligible checkpoint excerpt once. |
| Context-use threshold | Optional Claude function variant | `turn.complete` checks usage and invokes `$.session.compact()` at the configured percentage. `session.compact` supplies retained messages when the result meets the reduction floor; otherwise use native compaction. |

The generic `system_one_verify`, `find`, `rerank`, `classify`, `decide`, `compare` and `extract` tools are selected proactively by the main model **when relevant**. There is no deterministic event meaning “this paragraph needs semantic comparison” or “these options should be classified.” Policy injection and skill descriptions enable this behavior, but cannot guarantee that the model chooses every appropriate tool. Running all tools after every message would be wasteful and often ill-defined.

## Verification is based on observations, not claims

A ledger records matching `PreToolUse` and result events. A passing check is fresh only when it began after the most recent completed mutation. Checks still running are not passes. A failed command remains unresolved until that same command succeeds; a different passing lint command does not erase a failing test. The shell recognizer is conservative but not a full shell/program interpreter. It cannot infer every mutation hidden in arbitrary scripts or custom tools.

Completion checking first applies the evidence-aware belay judgment when verification is absent, stale, pending or failing. After suitable fresh checks, automatic review sends the original task, observed edit inputs, actual check evidence and the final message as a **claim** to `system_one_gate`'s implementation. The final message is never its own supporting evidence. This reviews observed edits, not an independently fetched full Git diff or all repository files.

Model advice cannot establish that a test ran or that a patch is correct. `review`/`escalate` can request inspection and additional evidence, but the agent must identify substantiated issues rather than invent defects to satisfy a model. Explicit partial or blocked progress is not forced into an endless completion loop.

Checks after a Stop continuation are reevaluated when the evidence changes. Exact repeats, a cooldown and a per-session block cap bound continuation. A successful identical review is cached by complete evidence/final-message/event digest. Do not modify these guard files to manufacture approval.

## Evidence sources and gaps

Structured event evidence is preferred. A supported transcript parser remains a compatibility fallback for sessions that did not receive a prompt-start event, and for subagent transcripts. A partial or unsupported transcript does not certify verification.

Missing start events, malformed observations, size limits and lost events mark evidence incomplete rather than silently trimming it into a confident verdict. A new real user prompt resets the ledger. Native compaction does **not** reset edit/check evidence. Tool observations carrying a shared session and `agent_id` are also mirrored into an existing parent ledger, preserving parent/child edit/check ordering. Separate-session subagents without a shared identity are reviewed in isolation; the bridge does not invent unseen parent/child links.

The code reads a bounded amount of event/transcript data and writes only private bridge state. Event ledgers can contain local tool inputs/results; treat them as sensitive. They are never used as a replacement transcript for compaction, because they deliberately omit much of the conversation.

## Compaction limits that automation cannot remove

**Stable command hooks save/recover checkpoints; they do not replace active history in either host.** Native auto-compaction must remain enabled. Codex's documented PreCompact output has no replacement-message operation. Calling the MCP compact tool does not itself shrink the active context.

Only the opt-in Claude function variant implements replacement via the runtime's `session.compact` API. It also requests automatic compaction from `turn.complete`, without requiring a user slash command. It needs a supporting host and the function-hook feature flag. Do not install both the stable and function variants at once. The optional variant still installs the event tracking, task verification, subagent and screening command hooks; it excludes the stable PreCompact checkpoint hook to avoid duplicate compaction requests.

`SYSTEM_ONE_AUTO_COMPACTION=0` disables bridge retention/checkpoint work and the optional function override, **not** the host's own native compactor.

## Installation and upgrade

```bash
node bin/open-jev-bridge.mjs install --host both
node bin/open-jev-bridge.mjs doctor
node bin/open-jev-bridge.mjs automation-status --host both
```

Restart both clients. Review/trust the new and changed hook definitions in `/hooks`; the installer cannot and does not bypass that consent. Local hook definitions do not automatically transfer into a different cloud/container host.

An installation rerun in the **same checkout path** refreshes owned hooks and pristine skills, preserves unrelated hooks and user files, and does not duplicate MCP registration. User-edited skill bodies are not overwritten. When moving to a different checkout path, uninstall from the old checkout before installing the new one. Configuration, secret-file paths and checkpoints are preserved.

Nonsecret connection settings resolved during installation are persisted so that a host which filters environment variables still finds the configured URL/model. Inherited bearer secret values are not persisted. Use `--api-key-file /absolute/private/file` with permissions `600`, or explicitly forward the environment secret as documented in the README. The isolated Claude function runtime uses exported `SYSTEM_ONE_*` settings, not the Node configuration file.

## Controls

Defaults below apply to the direct/standard command hooks.

| JSON configuration | Environment | Default | Meaning |
|---|---|---:|---|
| `autoVerify` | `SYSTEM_ONE_AUTO_VERIFY` | true | Master switch for Stop/subagent/task completion checks. |
| `autoReview` | `SYSTEM_ONE_AUTO_REVIEW` | true | Additional patch/completion gate after fresh passing checks. Requires autoVerify. |
| `autoScreen` | `SYSTEM_ONE_AUTO_SCREEN` | true | Advisory screening on matched external result events. |
| `autoCompaction` | `SYSTEM_ONE_AUTO_COMPACTION` | true | Automatic bridge retention/checkpoint work on native compaction. |
| `compactAtPercent` | `SYSTEM_ONE_COMPACT_AT_PERCENT` | 60 | Optional Claude function variant's usage trigger; not a Codex context-limit setting. |
| `maxEventBytes` | JSON only | 32768 | Bound on a canonical event message. |
| `maxEvidenceBytes` | JSON only | 1000000 | Bound on one event ledger. |
| `maxEvidenceEvents` | JSON only | 512 | Bound on canonical event messages per task. |
| `evidenceTtlMs` | JSON only | 86400000 | Maximum age for using event evidence. |
| `screenMaxChars` | JSON only | 3000 | Maximum complete external result screened automatically. |

Boolean environment values accept `1`, `0`, `true` and `false`. `shadow` remains available for observing would-block completion judgments without enforcing them. The model-facing policy still recommends appropriate evidence-backed tool use when hook enforcement is disabled.

## Privacy and failure behavior

The selected provider is the only judgment endpoint. **Automatic patch review sends bounded observed edit inputs and check evidence, not merely counters.** With hosted Jev, that selected content leaves the machine; remote use requires explicit opt-in. Redaction is best effort, not a guarantee that source code contains no proprietary information. Set `autoReview:false` to disable automatic patch-content review, or use a local provider. External-result screening likewise sends the selected fetched text.

No hook executes a project test, applies a patch, changes permissions or bypasses approval. A Stop request tells the main agent to run a meaningful check through its normal approved tools. Backend failures, invalid answers, incomplete evidence and context-budget errors fail open rather than trapping the host. Diagnostics explicitly distinguish these outcomes from a completed review. A failing optional content screen does not corrupt previously recorded verification evidence.

`automation-status` performs an **offline direct-install readiness check**, not an inference probe. It reports configured events, unverified native trust, and bounded recent per-session hook observations. It includes no API keys, endpoints, code or test-output content. Native/plugin-manager installs must also be checked in the host's own plugin and hook menus. A configured hook is not proof that a running host loaded or trusted it.

## Reproduce the automatic integration tests

```bash
npm run test:automation
npm run validate
```

The event-only tests exercise the real generated hook commands in separate Node processes and make real loopback HTTP calls. An explicit host double drives the lifecycle; **no manual MCP call is used to satisfy verification or initiate compaction**. The suite checks continuation and corrective verification, task exit-2 control, subagent isolation, automatic screening, native-auto PreCompact checkpoint recovery, provider profiles and bearer headers, upgrades, incomplete evidence and no-recursion behavior.

The optional Claude function adapter is tested through its registered `turn.complete` callback and a real HTTP fixture. This is a function-runtime contract harness, not an actual installed Claude runtime. Live Jev credentials, loaded Kev/Laya models and authenticated native-client sessions were not available in the build environment. Follow the native acceptance steps in TESTING.md on the actual deployment.
